# 為什麼分散式系統的時間總是說謊

每個剛接觸分散式系統的工程師都會以同一種方式被打臉:他們以為時間是一個可信賴的東西。實際上,在分散式系統裡,時間是最不可信的訊號之一。本文整理幾個常見的誤解,以及對應的應對策略。

## 物理時鐘的不可靠性

伺服器上的物理時鐘(石英晶體)會漂移。即使配備 NTP 同步,精度也只有毫秒等級。在一個高吞吐量的系統裡,一毫秒可以發生幾百次操作 — 這意味著兩台機器看到的「同一時刻」可能相差數百個事件。

更糟的是,NTP 偶爾會把時鐘「跳」一下,可能往前或往後。如果你的程式以為時間單調遞增,這個跳變就會炸掉你的測試、你的計費、你的排序、甚至你的鎖。

```python
# 不要這樣寫
start = time.time()
do_work()
elapsed = time.time() - start  # 可能是負數!
```

正確的做法是用單調時鐘(monotonic clock):

```python
start = time.monotonic()
do_work()
elapsed = time.monotonic() - start  # 永遠 >= 0
```

## 因果關係比時間重要

Leslie Lamport 在 1978 年的論文 "Time, Clocks, and the Ordering of Events in a Distributed System" 提出了一個關鍵觀察:在分散式系統裡,我們真正關心的不是事件發生在什麼物理時刻,而是事件之間的**因果關係**。

如果事件 A 「導致」事件 B,那麼任何觀察者都必須看到 A 在 B 之前發生。反之,如果 A 和 B 之間沒有因果關係,它們可以以任意順序被觀察。這就是「happens-before」關係。

Lamport 時鐘是一個簡單的計數器:每個節點維護一個本地計數器,每次本地事件遞增,每次收訊息時取 max(本地, 訊息) + 1。這保證了因果順序,但不保證並行事件的順序 — 而並行事件本來就沒有「真實」順序。

## Vector Clock 與 CRDTs

Vector clock 是 Lamport 時鐘的擴展:每個節點維護一個向量,記錄它對所有其他節點時鐘的最佳估計。Vector clock 不僅能判斷因果順序,還能判斷兩個事件是否並行。

這個能力是 CRDT(Conflict-free Replicated Data Types)的基礎。CRDT 利用 vector clock 的並行性偵測能力,讓不同節點對同一個資料的修改能無衝突地合併。

舉個例子:一個分散式 counter,如果每個節點維護自己的 counter 並用 vector clock 標記,合併時就是把所有節點的 counter 加總。這個操作是滿足結合律與交換律的,合併順序不影響結果。

## 真實系統的妥協

純粹的 vector clock 在大規模系統裡有實作上的問題:vector 大小與節點數成正比,在數千節點的系統裡,每筆訊息都要帶上幾 KB 的 vector,這是無法接受的開銷。

實務上,系統會做各種妥協:有些用 truncated vector clock,有些用 hybrid logical clocks(HLC),有些乾脆放棄並使用 server-assigned timestamps 加上 conflict resolution policies。

Google Spanner 採取了一個極端的解法:用原子鐘和 GPS 同步硬體時鐘,把時鐘誤差壓到幾毫秒以內,然後在每筆交易等待這個誤差時間,確保提交順序就是時間順序。這個做法叫 TrueTime。代價是需要專屬硬體基礎建設。

## 給應用層的建議

如果你在開發一般應用,而不是 Spanner 等級的基礎建設:

第一,任何「時間戳」儲存到資料庫之前,先想清楚:你真正想記錄的是「發生時刻」還是「事件順序」?如果是順序,用單調遞增的 ID 比用時間戳安全很多。

第二,不要假設兩台機器的時間是同步的。任何跨機器的時間比較都是潛在的 bug。如果一定要比較,用 server-assigned timestamp 配上 NTP 監控,並接受誤差。

第三,在 UI 上顯示時間時,接受時鐘並非完美。「剛剛」「幾分鐘前」這類相對表達比絕對時間更實用,也更能容忍時鐘誤差。

第四,寫測試的時候,假設時鐘會跳。`freezegun` 或 `mock-time` 這類工具能幫你模擬時鐘異常,確保你的程式對時間異常有韌性。

## 結語

分散式系統的時間問題沒有終極解法,只有不同程度的妥協。瞭解這些妥協,選擇適合你系統規模和需求的策略,比追求「完美的時間同步」更實際。

時間在分散式系統裡會說謊,我們的工作是讓系統在謊言中仍然能做對的事。
