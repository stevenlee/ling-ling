# On Learning Programming Languages As You Get Older

The first programming language is hard because programming is hard. The fifth language is hard for an entirely different reason: by then you have built up enough scar tissue from previous languages that you are simultaneously learning the new language's syntax and unlearning the assumptions baked into your fingers from the languages that came before. The sequence in which you encountered languages matters more than people realize, and so does the gap between them.

When I started, I learned C before any high-level language. That meant my mental model of memory was correct from day one. Pointers were not mysterious; they were the obvious way the machine worked. I had to unlearn this when I moved to Python, where the operative metaphor is references-to-objects-with-reference-counting and pointer arithmetic is meaningless. The unlearning was harder than the learning. For two years I wrote Python that looked, at the level of variable lifetimes and copying behavior, like C with garbage collection. It worked, but it was not idiomatic Python, and I could feel the friction every time I read a colleague's more pythonic code.

Then I learned Ruby, which is in many ways Python with smoother edges and a richer metaprogramming story. I learned almost nothing new about computation from Ruby; I learned about a community's taste. The Ruby community valued elegance in a way the Python community did not, and that taste was contagious. After Ruby I went back to Python and started writing better Python — not because Python had changed, but because I had changed my taste.

Then came Go. Go was a shock. Coming from Python and Ruby, where the dominant style is "write what you mean and trust the framework to figure it out," Go felt punishingly explicit. Errors must be handled at every level. There are no exceptions. There are no generics (at the time I started). The standard library makes choices that feel arbitrary until you've used them for a year, after which they feel obvious. Go forced me to confront how much I had been outsourcing decisions to language and framework defaults. After Go, my Python got more explicit too. Less magic, more boring, more reliable.

Rust came next, and Rust was the hardest of all because Rust is the language that refuses to let you lie to yourself about what your program is doing. The borrow checker is a tutor with infinite patience and zero mercy. You cannot half-understand ownership in Rust; either you understand it and the compiler agrees, or you don't and the compiler tells you why. The first three months were brutal. After that, the Rust I'd written started feeling like the only honest code I had ever produced. I'd be writing Python again, and I'd notice myself wondering "who owns this, who can mutate it, when does it die," questions I'd been blithely ignoring my entire career.

The thing nobody told me when I started is that learning a language well changes how you write in every other language you know. Not in the trivial "borrow this idiom" sense, but in the deeper sense of changing what you notice and what you ignore. After Go, I noticed boilerplate I had been overlooking. After Rust, I noticed lifetimes I had been ignoring. After Haskell, I noticed side effects I had been pretending didn't exist. Each new language adds another lens, and the lenses don't go away when you switch back.

This is also why "polyglot programmer" is a slightly silly label. It implies you can pick a language out of a toolbox like a screwdriver and apply it to a problem. Languages don't work like that. The language you're fluent in shapes what problems you see and how you frame them. Someone who is fluent in three deeply different languages thinks differently from someone fluent in three superficially different ones. The "polyglot" label conflates these.

I want to push back on one piece of common career advice: the idea that experienced engineers should "specialize" in one language and stop dabbling. This advice is well-meaning but I think wrong. The cost of learning your sixth language is much lower than the cost of learning your second, because most of the cost of language learning is conceptual, and the concepts transfer. The benefit, on the other hand, is largely orthogonal to language count: every genuinely new paradigm gives you a tool that none of your other languages provide. Stopping at three languages because "you're an expert now" is leaving the highest-leverage learning on the table.

What I'd suggest instead: every two or three years, learn a language that violates one of your assumptions. If you only know imperative languages, learn a functional one. If you only know statically typed languages, write a non-trivial program in a dynamic one. If you've never written a language with manual memory management, write enough Rust or C to get comfortable. If you've only used languages with mutable state, spend three months in Haskell or Clojure. The point isn't to add it to your resume; the point is to add it to your repertoire of thinking.

There's a version of this argument that gets made about natural languages too: that learning a second human language changes how you think in the first. I'm not sure that argument is true at the strong level it's sometimes pitched, but the programming-language version is. The evidence is in your own code, before and after.

The other thing nobody told me: the languages I valued most as a beginner are not the ones I value most now. I once worshipped Python's expressiveness; now I find it a little too forgiving, a little too willing to let me write code that I will regret. I once thought Java was bureaucratic; now I admit that some of that bureaucracy is just honest accounting of what programs are actually doing. C felt low-level and dangerous as a student; now it feels honest in the same way Rust does, just without the safety net. Tastes change. They should. If your taste in languages hasn't shifted in five years, you probably aren't learning enough.

The languages I want to learn next are the ones I've been avoiding because they look uncomfortable. Erlang, for its actor model and its religious dedication to "let it crash." OCaml, for the ML family's approach to type inference and pattern matching done right. Forth, just to see what a stack-based view of computation does to my head. None of these are likely to become a daily driver, but each one is a lens I don't yet own. I'd rather collect lenses than collect lines of code in any single language.

The closing thought: programming languages are not interchangeable, but they are not incommensurable either. They are different views onto the same set of computational truths, and a working programmer benefits from having access to several of those views. The marginal value of the next view is not zero. It might even be your most important investment, after a certain point in your career, because the problems that will challenge you next are the ones your current toolkit can't see.
